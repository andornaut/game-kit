# Install and update design

Sections 1 to 3 record the v0.56.1 baseline from Ada the Navigator's defect report and headless Chromium reproduction, Archie's install audit (policy 93aa783), and Chibi Tech's audit (main 5b8839cf). The baseline policies were "Installs" (93aa783) and "Updates" (1d4bd25). Section 4 describes the architecture. Sections 5 to 7 preserve the original migration, qualification plan and decisions. Paths in the baseline are relative to `src/web/pwa/` unless shown otherwise. Related work includes [gk-0006](work/gk-0006.md), [gk-0007](work/gk-0007.md), [gk-0008](work/gk-0008.md), [gk-0009](work/gk-0009.md).

## 1. Summary

Root cause of the fresh-install failure: the verified-JSON header allowlist. Through Cloudflare, browser fetches carry `priority` and `server-timing`, which are in neither `JSON_SOURCE_HEADERS` nor `DATA_SOURCE_HEADERS` (dom/serviceWorker.ts:95-117). `safeJsonSource` rejects any other header name (132-135), `fetchIntoCache` throws "Unsafe verified JSON response semantics" (384-389), and the install rejects after 46 s (862-871). Cloudflare adds these headers only over HTTP/3, and Android Chrome uses QUIC, so h2 and HTTP/1.1 tests pass. The 0.58.1 rule also ignores HTTP/1.1 `connection` and `keep-alive`. The approved hotfix (0.58.1) ignores unknown headers and rejects only those with body or cache-identity semantics: `clear-site-data`, `content-disposition`, `content-location`, `content-range`, `refresh` and `set-cookie`. It ships separately; this design only references it.

The rest is policy and scaling. v0.56.1 downloads inside one service-worker `install` event at 4 low-priority lanes and resumes only by re-hashing every stored file. Activation and the switch re-hash the build up to four more times, partly under a 10 s deadline. A `null` selection and a non-expiring group lock each break all later navigations or installs. An update from 833b2c63 to db59176b re-read and SHA-256 hashed 4,333 reused files to refetch 5 (2.2 MB). Proposal: the page downloads under the one loading screen, the worker becomes a build-agnostic router, and activation is one atomic record write plus a reload.

**Confirmed scaling failure (Ada reproduction, 2026-11-18).** On a 3G-like link (300 ms, 1.6 Mbit/s) with the header gate out of the way, Chromium killed the install at exactly 300.0 s ("ServiceWorker failed to install: The ServiceWorker timed out") with 2542 of 4338 files stored. 0.58.1 does not fix slow-mobile first installs; only the page-driven, resumable installer in 0.59.0 does, and the complete up-front install (about 8,340 files) makes the single-event path worse. A deploy during install fails it ("Content hash ... for /play/"), so each install pins one build. The switch took 9.4 to 12.3 s against the 10 s limit even at 4 CPUs. The games' existing browser smoke tests run over plain http and never register a worker; Ada is adding an install, update and offline check against a header-exact server with the Cloudflare h3 headers.

## 3. Gaps to policy

1. First install incomplete (Ada) or after home in the background (Archie, Chibi); not verified before play; first session uncontrolled.
2. Two progress runs with indeterminate phases.
3. Download inside one SW event, low priority, no cheap resume. This is a scaling risk: about 4,300 files took 46 s unthrottled, and a Slow 4G install over h2 ran 292 s without the worker being killed. That run failed because production redeployed `/play/` mid-install. A 3G run past 300 s is pending.
4. The in-session offer shows only on home, does not pause play and reappears after dismissal. No "staging complete" signal exists for showing Update now wherever the player is. Silent launch activation exists but costs up to 20 s (K5).
5. Reuse re-hashes every unchanged file (4,333 for a 5-file update).
6. Switch re-stages, re-hashes, can download, misses 10 s.
7. Sticky failures (9, 10); background-update failure shows Loading failed (K3); "Missing document build pin" under older workers (C7); Update now reloads with no awaited save, losing in-stage progress (C6).
8. Caches accumulate (K4); 20 s legacy launch stall (K5).
9. `/` never registers the worker (Archie A1, game-owned; kit must offer the call). Install is offered before registration (C8).
10. Ada's 8,340 requests: count dominates bytes.

## 4. Design

### Components

- `build/precachePlugin` records hash and size for every URL. It emits `/.game-kit/manifest-<version>.json`, a pointer at `/.game-kit/build.json` with `schema`, `version`, `buildId` and `manifest`, and optional packs. Configure the host to serve the pointer with `Cache-Control: no-store`. The worker reads installed build metadata from storage.
- `dom/storage/buildStore` owns the cache layout, records and reclamation.
- `dom/transfer/buildInstaller` fetches, verifies, stores and resumes builds.
- `dom/launch/launch` runs the loader, update discovery and in-session Update now. See the migration table for the APIs it replaced.
- `dom/routing/serviceWorker` serves the client's pinned build or the build named by `active`. It uses `skipWaiting` and `clients.claim`. The page owns install and staging downloads. `no-store` requests bypass the router. Files under `hashedAssetPrefix` use the default cache mode, so the HTTP cache or the router may answer those requests. The router prunes closed clients' pins on activation and on navigation at most once a minute, sparing pins written within that minute.

**Driver (decided).** The page installer drives the download, under the visible loading screen: 6 lanes, default priority, 3 attempts, 30 s inactivity timeout, no SW event held open. Updates use the same installer in background mode: 2 lanes, `low`, paused while hidden.

**Sound formats.** The page passes `createLaunch`'s `soundFormat`, chosen by the game (for example with `canPlayType`), as 0.58 passed `?sound=<format>` on the worker URL. The manifest lists every alternative; an alternative's format is its URL extension. The page reduces the pinned manifest to the alternatives in that format, none of a sound without one, plus every non-sound file (`buildRecords`' `installedManifest`), and saves the reduced manifest with the format recorded. The installer, progress, the store's completeness check, launch and the router's staged promotion all read that saved manifest, so they agree per build. A saved manifest for another format is replaced from the network manifest. A left-out alternative requested later goes to the network. `undefined` installs every alternative.

**Sound-format groups.** With `updateGroup`, the producer puts each format's sound alternatives in their own group under the returned name and tags it with `soundFormat` in the pointer. Grouped first installs and updates reduce the pointer to the groups without a format plus those in the page's format (`buildRecords`' `installedPointer`). Progress, the sealed group marker, completeness, staged promotion and the router read that reduced pointer. A marker sealed for another format, the same build with the same groups without a format, does not conflict: install or staging stores the new format's groups beside it, reusing shared groups by digest, and sealing replaces the marker in one write under the build-state lock. The other format's groups stay until the build is reclaimed, so a router snapshot that still reads them keeps working. Activation and staging still require the device format's marker. Before activation or publishing `staged`, launch checks that every stored member is a manifest file of its size and that every file of `installedManifest(soundFormat)` is stored. Untagged groups from earlier builds may also hold left-out alternatives and still pass. A grouped sound request missing from a router snapshot can use a recovered sound group for the same version. Otherwise an unlisted alternative goes to the network. An origin can serve archive-only members to pages without an installed build through `createGroupArchiveMemberReader`, which verifies the whole group archive against the pointer before serving a member.

**Active-build audio recovery.** If the device's sound format changes, online startup can recover audio for the still-deployed active build when the controlling worker supports repair. The page reuses shared groups, verifies the selected members and rechecks the active and staged records before sealing. This keeps the selected build and its client pins. Offline startup and failed repair continue into play without unavailable sounds.

**Layout.** `<prefix>build-<version>` per build; `<prefix>records` holds `active`, `staged` and client pins. Entries are written only after size and SHA-256 pass, with header `x-game-kit-sha256`; `Cache.put` is atomic, so presence plus header proves verification.

**Resume.** The installer reuses files present with matching digest headers and repairs missing or mismatched entries without re-hashing the reused bodies.

**Pinned manifest (decided).** Each install reads `build.json` once and pins that manifest. If a file's bytes stop matching it, or the file is gone (404 or 410), because the game redeployed mid-install, the installer re-reads `build.json` and restarts on the new manifest, reusing every verified entry by hash, so only changed files are fetched again. The document that started the install came from the old build, so once the new build is active it reloads once into it rather than play (at most once per build, carried in `sessionStorage`). The page takes its document's build to be the first `build.json` it read. Game deploys are unchanged.

**Progress.** One determinate value in [0, 1]. Total = bytes to fetch + bytes of boot files read afterwards (all sizes are in the manifest). The installer reports received bytes; the Phaser loader reports settled files as their bytes; the record write is the last 1%. The document the first install reloads into reports the carried value as soon as `run()` restores it. No valueless phases.

**Verification.** Downloaded files are verified while streaming. Completion checks that every manifest file is present with its matching digest header. `storage.persist()` and `estimate()` run first, failing early on quota.

**Activation and switch.** First install writes `active=<version>` and boots from cache in a claimed, controlled session. An update writes `active=<staged>` and reloads (Update now) or is promoted at launch (below). A navigation uses its resulting client's pin when present. Otherwise the router tries staged promotion and reads `active`. A navigation whose URL is absent from the selected build goes to the network without a new pin. Participating pages and the router serialize changes to the active and staged records where Web Locks is available. Other windows keep their pins. The launching page deletes builds neither active, staged nor pinned by a live client (K4).

**Updates.** The page checks `build.json` at launch and wakes discovery on visibility return, window focus and reconnect. Games call `createLaunch(...).requestUpdateCheck()` on genuine start-of-play and return-to-Start/Home transitions. The ordinary wake scheduler shares one 60-second cooldown and defers one eligible check for the remaining time while visible and online. Discovery is event-driven. A newer build stages into `build-<new>`, copying unchanged entries by digest header and fetching the rest before writing `staged`.

- Cold launch automatically activates a complete, verified staged build before game code or save initialization. On a routed document navigation with no resulting-client pin, the router checks completeness and rechecks the records before promoting and serving the build. A document reload handled by the router follows the same rule. Existing pinned windows keep their builds. If the page starts with a complete distinct staged build, `run()` can reload once into the router before gameplay.
- During a session, `onUpdateReady({version, updateNow, dismiss})` fires once per staged version per document, on any screen. The game draws the Update now prompt and pauses play. `updateNow(save)` awaits the game's save (C6), then checks that the offered build is still staged for the same active build. It reloads without downloading after activation or if the offered build is already active. A superseded offer rejects with `ObsoleteUpdateOfferError` from `runtime/web/pwa/buildContract`, leaving both records alone. The error's `version` names the offer that began the shared switch. Clear the prompt only if that version matches the accepted offer and the same offer is still displayed. An obsolete rejection from an earlier switch leaves a displayed successor actionable. Genuine save and switch failures keep the caller's error handling. The next ordinary check can report a successor that has not been offered to the game yet. On `dismiss()`, the game closes the prompt and restores the previous view, focus and pause state. The active build keeps serving, and the staged build remains available for cold launch.
- Start/Home and foreground returns in the same document only wake discovery. Newer-save recovery through `requireNewer()` is a separate automatic activation path. The game keeps gameplay, incompatible save loading and all save writes blocked until the new document proves compatibility.

**Failure and recovery.** An absent record has no cache entry. Navigation goes to the network when there is no active build. See the README's router contract for cache misses. First-install state (`onProgress`, `onFailure`) and background updates (`onUpdateState`) are separate channels. A failed background update retries silently while visible after 60 seconds, then doubles the delay up to 15 minutes. Hiding the page or disposing the launch cancels the timer. Loading failed covers foreground install failures and failed startup storage reads. Retry rereads startup state before deciding whether to resume an install. A failed read does not establish that the active record is absent. For an unsupported or quota-limited first install, `run()` calls `onNetworkPlay({ reason })` and resolves `play` for the game's network fallback. Without an active record, each later launch tries the install again and reuses verified entries. Before any of this, `prepareBrowserLaunch` requires Service Worker, Cache Storage and `DecompressionStream` on every production launch and otherwise shows the shared unsupported error with no Retry. `DecompressionStream` is checked for every build, not only grouped ones, because the pointer is read later and every browser in Vite's default build target provides it.

**Request packs (opt-in).** Set `precachePlugin`'s `packs: { maxBytes }` to a positive integer decoded byte limit. Omit the option to keep individual transfers. Each optional schema-1 manifest entry `packs: [{ url, members, encoding: "gzip", encodedByteSize }]` names a content-addressed `/.game-kit/pack-<digest>.bin` and its ordered member URLs. The producer emits deterministic gzip over the concatenated file bodies and omits packs whose envelopes are no smaller than their decoded bytes. The manifest's file sizes give the slice boundaries. Each member must pass size and SHA-256 checks before entering the cache at its original URL. Sound alternatives are grouped by format, and verified JSON families retain their individual response checks. The router continues to serve only manifest files.

After cache reuse, the installer uses a pack when at least two members remain and they account for at least half of both the pack's members and decoded bytes. Progress counts the downloaded envelope bytes. Missing decoder support or an unavailable or invalid pack falls back to the remaining individual files. Verified entries survive cancellation and retry. Manifests without pack metadata still install from individual URLs.

**HTTP representation.** Serve the emitted gzip envelope as `application/octet-stream` with identity HTTP encoding. The envelope is application data, so serving it as emitted needs no `Content-Encoding: gzip` header. If the server applies additional HTTP coding, its header describes that outer coding. Fetch removes the HTTP coding, then the installer checks the exact envelope length and uses `DecompressionStream("gzip")` with the manifest's decoded byte bound. The installer requests packs from the same origin with redirects refused and bypasses the service worker cache.

**Group transport.** A static group's pointer entry keeps `byteSize` and `sha256` of the decoded archive, which names the group, keys its cache entry and drives reuse, and adds `encoding: "gzip"` and `encodedByteSize`. The producer emits one deterministic gzip member (level 9, zero timestamp, unknown OS byte) at `/.game-kit/group-<sha256>.bin`. The page reads exactly `encodedByteSize` bytes, decodes them with `DecompressionStream("gzip")` into exactly `byteSize` bytes, verifies the SHA-256 and only then stores the decoded archive, so the router, reuse and the group marker are unchanged. Progress counts transport bytes. The marker omits the transport, so a build staged from either transport matches its pointer. Serve the files like packs. Recipe groups have no encoding and keep the decoded archive as their transport. During the migration from 0.72.0 the build also emits each decoded archive at `buildArchivePartUrl(group, 0)` for pages that predate the transport, unless the game sets `precachePlugin`'s `omitDecodedGroupCopies: true` once its installed devices have staged a build from 0.73.0 or later (`CLEANUP (added 2026-11-25)`: remove the copies and the option once every grouped game sets it).

**Transfer qualification.** Treat 1–2 MB as a trial range. Before choosing a default, compare requests and encoded response-body bytes for identical members on the delivery route, including its actual compression of individual files. Record observed `Content-Type`, `Content-Encoding`, `Content-Length` when present, and `Vary`. File shape alone gives no evidence that CDN compression is active.

**Asset groups (decided).** Removed in 0.59.0, with groupStore and the activation barrier. The complete build installs up front.

**Pre-router cache migration (historical).** The original router launch installed under the loader, re-hashed and copied entries from old caches, and deleted old routing records, the group database and caches after recording `active`. Version 0.69 removed that migration. The decoded group copy migration above still applies.

## 6. Original rollout and qualification plan

0. 0.58.1: the decided header hotfix (unblocks Ada fresh installs; 0.57.0 and 0.58.0 are already released).
1. 0.58.2 (non-breaking): fix 9 (write the selection only after verification) and 10 (expire `activating` at its deadline). Decided. Stuck devices then recover on their next worker update.
2. 0.59.0 (breaking): router, installer, launch loader, silent launch promotion, Update now, K3 split and full hashes. Consumer adoption branches for all three games.
3. 0.61.0: release the ready UI and ordinary update discovery APIs.
4. A later minor adds packs, sized from Art's sheet measurement.
5. A later release removes the legacy CLEANUP.

### Tests

- Unit: verified JSON passes with unknown Cloudflare headers (`priority`, `server-timing`) and HTTP/1.1 `connection` and `keep-alive`, and fails on each of the six rejected headers; an unpinned client is served `active`; reuse performs no digest; resume after a kill mid-file and mid-record, hash mismatch, deploy mid-install, quota failure, record atomicity, delta reuse, reclaim with pins.
- Header coverage: run the install over HTTP/3 against the Cloudflare-served deploy, or replay recorded h3 response headers. h2 and HTTP/1.1 runs do not exercise the failure.
- Switch: at 1 CPU, Update now reloads within the bound with no re-hash.
- Container Playwright Chromium (stock launcher, `npm run test:e2e`), with CDP network throttle (about 1.6 Mbps, 300 ms) on every page and service worker, 4x CPU throttle on every page and Cloudflare's h3 headers on every response. The long run (`npm run test:e2e:long`, about 68 MB) asserts the 5 min bound. The short run asserts the rest in CI. Both fixtures stay under the specific-file cap. Assert:
  - the install exceeds 5 min wall time and completes;
  - the install fetches and stores only the sound alternatives of the page's `soundFormat`;
  - a reload and `ServiceWorker.stopWorker` mid-install resume with no repeat requests;
  - play works offline afterwards;
  - an update fetches only the delta;
  - a redeploy mid-install does not fail the pinned install, and a controlled old document reloads into the new build with no 404;
  - when staging completes mid-session, `onUpdateReady` fires once on any screen, with a test game prompt that pauses play, while `dismiss()` leaves the active build serving;
  - the next launch promotes silently with zero requests and no prompt;
  - `updateNow(save)` awaits `save` before it switches, with zero requests;
  - a failed background update shows no Loading failed.
- Consumer proof on all three games. User real-device checks on Android.

**Risks.** The 5-minute single-event limit stays a scaling risk until 0.59.0 removes the event-bound download. Android freezes background tabs, so updates stall until the next visit (resumable). Eviction without `persist()`. Large files are hashed in memory. Slow devices currently pay a 10 s launch lookup until 0.59.0. The record schema must stay compatible across kit versions. The CDN must never cache `build.json`.

## 7. Decisions

DECIDED (user):

- Driver: page installer with a router-only worker.
- Defects 9 and 10: patch now as 0.58.2.
- Asset groups: remove in 0.59.0.
- Request batching: kit packs plus Art sheets, in a later minor after the measurements.
- Update discovery: the page fetches `build.json`.
- Update now presentation: game-rendered; the kit fires `onUpdateReady({version, updateNow(save), dismiss})`.
- Archie G2: once installed, boot loads every group behind the one loader.
- 0.58.2 switch stopgap (defect 8): skip re-hashing entries already verified at install; check presence and recorded size only.

No open decisions remain.
