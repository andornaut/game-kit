# Install and update design

Sources: Ada the Navigator defect report and headless-Chromium reproduction (v0.56.1), Archie install audit (policy 93aa783), Chibi Tech audit (build of main 5b8839cf, received). Policy: game-policies.md "Installs" (93aa783) and "Updates" (1d4bd25). Code: game-kit v0.56.1. Paths are relative to `src/web/pwa/` unless shown otherwise. Work items: [gk-0006](work/gk-0006.md), [gk-0007](work/gk-0007.md), [gk-0008](work/gk-0008.md), [gk-0009](work/gk-0009.md).

## 1. Summary

Root cause of the fresh-install failure: the verified-JSON header allowlist. Through Cloudflare, browser fetches carry `priority` and `server-timing`, which are in neither `JSON_SOURCE_HEADERS` nor `DATA_SOURCE_HEADERS` (dom/serviceWorker.ts:95-117). `safeJsonSource` rejects any other header name (132-135), `fetchIntoCache` throws "Unsafe verified JSON response semantics" (384-389), and the install rejects after 46 s (862-871). Cloudflare adds these headers only over HTTP/3, and Android Chrome uses QUIC, so h2 and HTTP/1.1 tests pass. The 0.58.1 rule also ignores HTTP/1.1 `connection` and `keep-alive`. The approved hotfix (0.58.1) ignores unknown headers and rejects only those with body or cache-identity semantics: `clear-site-data`, `content-disposition`, `content-location`, `content-range`, `refresh` and `set-cookie`. It ships separately; this design only references it.

The rest is policy and scaling. v0.56.1 downloads inside one service-worker `install` event at 4 low-priority lanes and resumes only by re-hashing every stored file. Activation and the switch re-hash the build up to four more times, partly under a 10 s deadline. A `null` selection and a non-expiring group lock each break all later navigations or installs. An update from 833b2c63 to db59176b re-read and SHA-256 hashed 4,333 reused files to refetch 5 (2.2 MB). Proposal: the page downloads under the one loading screen, the worker becomes a build-agnostic router, and activation is one atomic record write plus a reload.

**Confirmed scaling failure (Ada reproduction, 2026-11-18).** On a 3G-like link (300 ms, 1.6 Mbit/s) with the header gate out of the way, Chromium killed the install at exactly 300.0 s ("ServiceWorker failed to install: The ServiceWorker timed out") with 2542 of 4338 files stored. 0.58.1 does not fix slow-mobile first installs; only the page-driven, resumable installer in 0.59.0 does, and the complete up-front install (about 8,340 files) makes the single-event path worse. A deploy during install fails it ("Content hash ... for /play/"), so each install pins one build. The switch took 9.4 to 12.3 s against the 10 s limit even at 4 CPUs. The games' existing browser smoke tests run over plain http and never register a worker; Ada is adding an install, update and offline check against a header-exact server with the Cloudflare h3 headers.

## 3. Gaps to policy

1. First install incomplete (Ada) or after home in the background (Archie, Chibi); not verified before play; first session uncontrolled.
2. Two progress runs with indeterminate phases.
3. Download inside one SW event, low priority, no cheap resume. This is a scaling risk: about 4,300 files took 46 s unthrottled, and a Slow 4G install over h2 ran 292 s without the worker being killed. That run failed because production redeployed `/play/` mid-install. A 3G run past 300 s is pending.
4. The in-session offer shows only on home, does not pause play and reappears after dismissal. No "staging complete" signal exists for showing Update now wherever the player is. Silent launch activation exists but costs up to 20 s (K5).
5. Reuse re-hashes every unchanged file (4,333 for a 5-file update).
6. Switch re-stages, re-hashes, can download, misses 10 s.
7. Sticky failures (9, 10); background-update failure shows Loading failed (K3); "Missing document build pin" under older workers (C7); Update now reloads with no awaited save, losing in-stage progress (C6).
8. Caches accumulate (K4); 20 s legacy launch stall (K5).
9. `/` never registers the worker (Archie A1, game-owned; kit must offer the call). Install is offered before registration (C8).
10. Ada's 8,340 requests: count dominates bytes.

## 4. Design

### Components

- `vite/precachePlugin`: hash and size for every URL; emits immutable `/.game-kit/manifest-<version>.json`, a `no-store` pointer `/.game-kit/build.json` (`{schema, version, buildId}`) and optional packs. The worker no longer embeds the manifest.
- `dom/buildStore` (new): cache layout, records, reclaim.
- `dom/buildInstaller` (new): fetch, verify, store, resume.
- `dom/launch` (new): the one loader, silent launch activation and in-session Update now; replaces `startOfflinePlay` and `UpdateFlow`.
- `dom/serviceWorker` (router only): serves the build named by `active` or the client's pin; `skipWaiting` plus `clients.claim`; downloads nothing. A client with no pin is served `active` instead of throwing (C7). A `no-store` request, such as the installer's, goes to the network. It deletes the pins of closed clients at activate and on navigation at most once a minute, sparing pins written within that minute.

**Driver (decided).** The page installer drives the download, under the visible loading screen: 6 lanes, default priority, 3 attempts, 30 s inactivity timeout, no SW event held open. Updates use the same installer in background mode: 2 lanes, `low`, paused while hidden.

**Layout.** `<prefix>build-<version>` per build; `<prefix>records` holds `active`, `staged` and client pins. Entries are written only after size and SHA-256 pass, with header `x-game-kit-sha256`; `Cache.put` is atomic, so presence plus header proves verification.

**Resume.** After a reload or worker restart, the installer diffs `cache.keys()` against the manifest and fetches only absent keys, with no re-hash.

**Pinned manifest (decided).** Each install reads `build.json` once and pins that manifest. If a file's bytes stop matching it, or the file is gone (404 or 410), because the game redeployed mid-install, the installer re-reads `build.json` and restarts on the new manifest, reusing every verified entry by hash, so only changed files are fetched again. Game deploys are unchanged.

**Progress.** One determinate value in [0, 1]. Total = bytes to fetch + bytes of boot files read afterwards (all sizes are in the manifest). The installer reports received bytes; the Phaser loader reports settled files as their bytes; the record write is the last 1%. The document the first install reloads into reports the carried value as soon as `run()` restores it. No valueless phases.

**Verification.** Per file while streaming. Completion is a metadata check: key sets equal and header hashes match the manifest. `storage.persist()` and `estimate()` run first, failing early on quota.

**Activation and switch.** First install writes `active=<version>` and boots from cache in a claimed, controlled session. An update writes `active=<staged>` and reloads (Update now) or is promoted at launch (below). The router reads `active` per navigation: no lifecycle, handshake, `SWITCH_TIMEOUT_MS` or group lock. Other windows keep their pins. The launching page deletes builds neither active, staged nor pinned by a live client (K4).

**Updates (1d4bd25).** Discovery (decided): at launch and resume (60 s throttle) the page fetches `build.json`. If newer, it stages into `build-<new>`, copying unchanged entries by header hash with no re-hash and fetching the rest, then writes `staged`.

- At launch: when the router serves a launch navigation and `staged` is complete, it promotes `staged` to `active` and serves the new build. There is no prompt, handshake or reload, and it happens before any game code or save access. Windows still running keep their pins. As a fallback, `run()` reloads once if its document is older than a complete `staged`.
- During a session: when staging completes, `onUpdateReady({version, updateNow, dismiss})` fires once per staged version, on any screen. Presentation is game-rendered (decided): each game draws its own Update now prompt and pauses play. The kit ships no overlay. `updateNow(save)` awaits the game's save (C6), writes `active`, and reloads with no download. `dismiss()` resumes play on the active build. The offer is not shown again this session unless a newer build stages; the next launch promotes silently.
- The kit never activates in a running session except through `updateNow` or `requireNewer` (existing fences).

**Failure and recovery.** Records change atomically and only after verification; no "none" value exists. No `active`: navigation goes to the network. Evicted entries: the router fetches the matching hash as today and the next launch repairs under the loader. K3: first-install state (`onProgress`, `onFailure`) and background updates (`onUpdateState`: `staging`, `ready`, `failed`) are separate channels. An update failure is retried silently and never shows Loading failed or pauses play. Only the first install shows Loading failed, for a `network` or `verification` failure, and Retry resumes. A first install the device cannot complete, `unsupported` (the router cannot register) or `quota` (storage is full), shows no Loading failed: `run()` calls `onNetworkPlay({ reason })` once, resolves `play` and the game plays from the network under its own notice. With no `active` record, each later launch tries the install again, reusing stored entries.

**Request count (decided, 0.60.0).** Kit packs plus Art sheets: the plugin concatenates small files into 1 to 2 MB packs with a JSON index, and the installer splits them into per-URL entries, verifying each member, so runtime URLs are unchanged. Updates fetch changed members singly when few, else changed packs. This complements Art's packing of about 8,323 SVG frames into about 150 sheets and covers the remaining small JSON and audio files.

**Asset groups (decided).** Removed in 0.59.0, with groupStore and the activation barrier. The complete build installs up front.

**Legacy migration** (`CLEANUP (added 2026-11-18)`: remove once all three games deploy the router). The first router launch finds no `active` and installs under the loader, copying from old caches by re-hash once, then deletes old routing records, group DB and caches after `active` is written.

## 6. Rollout

0. 0.58.1: the decided header hotfix (unblocks Ada fresh installs; 0.57.0 and 0.58.0 are already released).
1. 0.58.2 (non-breaking): fix 9 (write the selection only after verification) and 10 (expire `activating` at its deadline). Decided. Stuck devices then recover on their next worker update.
2. 0.59.0 (breaking): router, installer, launch loader, silent launch promotion, Update now, K3 split and full hashes. Consumer adoption branches for all three games.
3. 0.60.0: packs, sized from Art's sheet measurement.
4. A later release removes the legacy CLEANUP.

### Tests

- Unit: verified JSON passes with unknown Cloudflare headers (`priority`, `server-timing`) and HTTP/1.1 `connection` and `keep-alive`, and fails on each of the six rejected headers; an unpinned client is served `active`; reuse performs no digest; resume after a kill mid-file and mid-record, hash mismatch, deploy mid-install, quota failure, record atomicity, delta reuse, reclaim with pins.
- Header coverage: run the install over HTTP/3 against the Cloudflare-served deploy, or replay recorded h3 response headers. h2 and HTTP/1.1 runs do not exercise the failure.
- Switch: at 1 CPU, Update now reloads within the bound with no re-hash.
- Container Playwright Chromium (stock launcher, `npm run test:e2e`), with CDP network throttle (about 1.6 Mbps, 300 ms) on every page and service worker, 4x CPU throttle on every page and Cloudflare's h3 headers on every response. The long run (`npm run test:e2e:long`, 4,500 files, 46 MB) asserts the 5 min bound; the short run (400 files) asserts the rest in CI. Assert:
  - the install exceeds 5 min wall time and completes;
  - a reload and `ServiceWorker.stopWorker` mid-install resume with no repeat requests;
  - play works offline afterwards;
  - an update fetches only the delta;
  - a redeploy mid-install does not fail the pinned install;
  - when staging completes mid-session, `onUpdateReady` fires once on any screen, with a test game prompt that pauses play, while `dismiss()` leaves the active build serving;
  - the next launch promotes silently with zero requests and no prompt;
  - `updateNow(save)` awaits `save` before it switches, with zero requests;
  - a failed background update shows no Loading failed.
- Consumer proof on all three games. User real-device checks on Android.

**Risks.** The 5-minute single-event limit stays a scaling risk until 0.59.0 removes the event-bound download. Android freezes background tabs, so updates stall until the next visit (resumable). Eviction without `persist()`. Large files are hashed in memory. Slow devices currently pay a 10 s launch lookup until 0.59.0. The record schema must stay compatible across kit versions. The CDN must never cache `build.json`.

## 7. Decisions

DECIDED (user):

- Driver: page installer with a router-only worker.
- Defects 9 and 10: patch now as 0.58.2.
- Asset groups: remove in 0.59.0.
- Request batching: kit packs plus Art sheets, in 0.60.0.
- Update discovery: the page fetches `build.json`.
- Update now presentation: game-rendered; the kit fires `onUpdateReady({version, updateNow(save), dismiss})`.
- Archie G2: once installed, boot loads every group behind the one loader.
- 0.58.2 switch stopgap (defect 8): skip re-hashing entries already verified at install; check presence and recorded size only.

No open decisions remain.
