## Scope

0.59.1: `retry()` in `src/load/loadingAttempts.ts` calls each tracked resource's `status()` outside its error handling, in `refresh()` and in the failed-resource loop. A throwing `status()` escapes `retry()` synchronously instead of rejecting its promise, and the retry stays in flight, so later retries wait on it. Treat a throwing `status()` like a failed `resource.retry()`.

## Criteria

- `retry()` never throws synchronously; a throwing `status()` rejects the returned promise.
- The flight is cleared, so the next `retry()` starts a fresh attempt.
- A regression test fails on 0.59.0 and passes with the fix.

## Decisions

- Ship as patch release 0.59.1 (user, 2026-11-19).

## Outcome

The failed-resource loop in `retry()` was the only exposed `status()` call: `refresh()` and every
other public path read status through the snapshot, which already counts a throwing check as
failed. The loop now catches a throwing `status()`, skips that provider's `retry()`, clears the
flight and rejects the returned promise with the first thrown error, so the next `retry()` starts a
fresh attempt. Regression tests cover a throw inside the loop and a throw that begins at the
initial refresh; both fail on 0.59.0.
